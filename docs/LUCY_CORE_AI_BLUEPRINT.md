#### 4. Mandatory Code Block Explanation Standard
Every future Lucy code block must include the following five-part explanation.
This applies to TypeScript, JavaScript, Python, Lua, SQL, C++, Unreal scripts, Blender Python, shell scripts, config files, FiveM manifests, Home Assistant automations, and any other executable or semi-executable block.

Required Format:
**WHAT THIS DOES:**
Explain the direct purpose of the code.

**WHY THIS EXISTS:**
Explain why Lucy needs this block in the architecture.

**HOW THIS WORKS:**
Explain the mechanics, data flow, inputs, outputs, and important assumptions.

**HOW TO CHANGE IT:**
Explain the safe way to modify the block, including which values are intended to be edited and which should not be touched.

**DEBUG EXAMPLE:**
Show a realistic failure, what the error might look like, where to inspect, and how Lucy/Randy should fix it.

This standard must appear directly above or directly below every meaningful code block.

#### 10. ToolchainManager Standard
ToolchainManager must not merely say whether something exists.
It must report:
```typescript
type ToolchainStatus = 'ready' | 'missing' | 'broken' | 'version_mismatch';

interface ToolchainEntry {
  name: string;
  status: ToolchainStatus;
  version?: string;
  requiredVersion?: string;
  path?: string;
  pathValid: boolean;
  healthCheckPassed: boolean;
  lastHealthCheckAt: number;
  notes?: string;
}
```
WHAT THIS DOES: Tracks whether a required build tool is ready, missing, broken, or version-mismatched.
WHY THIS EXISTS: Lucy must not claim she can build UE5, FiveM, Blender, Lua, Node, or C++ projects unless the needed tools actually work.
HOW THIS WORKS: Each tool gets a status, version, path, and health check result. Lucy checks both existence and executability.
HOW TO CHANGE IT: Add new tools by adding more ToolchainEntry records. Do not treat existence alone as ready.
DEBUG EXAMPLE: If UE5 is installed but Visual Studio Build Tools are outdated, Lucy should report version_mismatch or broken, not ready.

#### 11. BuilderSafetyGate Standard
BuilderSafetyGate must classify risk before edits, commands, deploys, restarts, deletes, installs, or database writes.
```typescript
type BuilderRiskLevel = 'low' | 'medium' | 'high' | 'critical';

interface BuilderSafetyDecision {
  allowed: boolean;
  riskLevel: BuilderRiskLevel;
  requiresApproval: boolean;
  approvalReason?: string;
  rollbackRequired: boolean;
  reason: string;
}
```
WHAT THIS DOES: Creates a formal safety decision before Lucy performs build or deployment actions.
WHY THIS EXISTS: A CSS edit, server restart, SQL migration, resource overwrite, and database wipe are not equal. Lucy must treat them differently.
HOW THIS WORKS: The safety gate scores the requested operation, determines whether approval is required, and checks whether rollback must exist first.
HOW TO CHANGE IT: Add more rules for new action types. Make production actions stricter than sandbox actions.
DEBUG EXAMPLE: Deleting a temp file is low risk. Restarting a live FiveM server is high risk. Wiping a database is critical and must require approval and backup verification.

#### 13. RuntimeLab Standard

interface ReplayableRuntimeSession {

#### 14. VisualVerification Standard
VisualVerification must return confidence, not just pass/fail.
```typescript
interface VisualVerificationResult {
  passed: boolean;
  visualConfidence: number;

```
WHAT THIS DOES: Scores whether UI, map placement, texture output, screenshots, or visual build results look correct.
WHY THIS EXISTS: Compiling does not mean working. A UI can compile and still be unreadable. A map can stream and still be misplaced.
HOW THIS WORKS: Lucy compares screenshots, checks contrast, layout, object placement, texture presence, and visible anomalies.
HOW TO CHANGE IT: Add domain-specific checks for FiveM NUI, UE5 viewport screenshots, GTA V interiors, and map mods.
DEBUG EXAMPLE: If a menu renders but the text blends into the background, Lucy marks visual confidence low and recommends a CSS contrast fix.

#### 15. BuilderMemory Standard
BuilderMemory must track success rate.
```typescript
interface BuilderMemoryRecord {
  id: string;
  domain: 'fivem' | 'ue5' | 'gta5_map' | 'general_code';
  patternName: string;
  problem: string;
  solution: string;
  successRate: number;
  failureCount: number;
  lastOutcome: 'success' | 'failure' | 'partial';
  filesAffected: string[];
  confidence: number;
  lastUsedAt: number;
}
```
WHAT THIS DOES: Stores reusable build patterns and tracks whether they actually worked.
WHY THIS EXISTS: Memory without scoring becomes superstition. Lucy must prefer patterns that succeeded.
HOW THIS WORKS: Every build/fix outcome updates the record’s success rate, failure count, confidence, and last outcome.
HOW TO CHANGE IT: Add new domains or tags for Randy’s specific servers, projects, frameworks, or toolchains.
DEBUG EXAMPLE: If an ox_inventory item registration fix worked three times and failed once, Lucy stores that pattern with its success rate and applies it carefully next time.

HOW THIS WORKS: Every artifact gets an ID, path, checksum, summary, and related artifact links.
HOW TO CHANGE IT: Add new artifact types as Lucy gains new build domains.
DEBUG EXAMPLE: A FiveM release zip links to the diff, SQL migration, NUI screenshot, server log, validation report, and rollback snapshot.
